# Access Agent - Accessibility Assessment Agent

A tool that scans a website URL for accessibility issues, using Playwright + axe-core for detection and a local LLM for on-demand, plain-language explanations and fixes — mapped against WCAG 2.2.

## Problem Statement

Automated accessibility scanners like axe-core catch real violations but present them as a raw, unexplained rule dump. Understanding what a violation means, why it matters, and how to fix it usually requires WCAG expertise most developers don't have. Access Agent adds a fast, deterministic layer that maps each violation to its real WCAG 2.2 criterion, plus an on-demand LLM explanation for any finding a developer wants to understand better.

**Intended users:** developers who want a clear, usable accessibility report for a URL without first becoming WCAG experts.

## Tools & Frameworks Used

- **LangGraph** — orchestrates the pipeline: planner → DOM scan → aggregator → report
- **Playwright** — headless browser automation to render the target page
- **axe-core** (via `axe-core-python`) — automated WCAG rule engine and detection layer
- **Ollama** (default) — local, open-source LLM used specifically for on-demand, per-finding explanations. **No paid API required.**
- **Claude API** (optional) — alternate provider via the same `get_llm()` interface
- **Streamlit** — web UI
- **Pydantic** — schema validation, including deterministic WCAG level/name/reference lookups
- **pytest** — automated test suite

## How It Works

1. Enter a URL and click **Scan**. Playwright renders the page and axe-core scans it for violations.
2. Findings are deterministically deduplicated and mapped to WCAG 2.2 criteria and conformance levels using axe-core's own rule tags — not LLM guesses. This keeps scanning fast regardless of how many issues a page has.
3. Expand any finding to see its WCAG criterion, level, and a link to the official W3C reference. Findings with no real WCAG mapping are labeled as best-practice recommendations, not WCAG violations.
4. Click **"Explain this issue"** on any finding for an on-demand, plain-language explanation and a concrete suggested fix, generated by the local LLM specifically for that finding's actual selector and context.

## Setup

1. **Clone the repo and install dependencies:**
```bash
   git clone <your-repo-url>
   cd <repo-folder>
   uv sync
```

2. **Install the Playwright browser:**
```bash
   uv run playwright install chromium
```

3. **Install Ollama, pull the model, and make sure it's running:**
```bash
   ollama pull qwen3:8b
   ollama serve
```
   (Ollama may already run in the background after installing the desktop app.)

4. **Create your `.env` file** by copying the provided template:
```bash
   cp .env.example .env
```
   The defaults work as-is with no API key needed. `.env` is listed in `.gitignore` so your local configuration is never committed. To use a different local model, pull it with Ollama and set `OLLAMA_MODEL` in `.env` to match.

   *(Optional: to use Claude instead, set `LLM_PROVIDER=anthropic` and add your `ANTHROPIC_API_KEY`.)*

5. **Run the app:**
```bash
   uv run streamlit run app.py
```

## Example

**Input:** a real URL entered in the Scan form.

**Output:** a severity-sorted list of findings, e.g.:

> **[SERIOUS]** Ensures the contrast between foreground and background colors meets WCAG 2 AA contrast ratio thresholds
> WCAG Criterion: 1.4.3 — Contrast (Minimum) (Level AA)
> Affected element (CSS selector): `.frb-iad`

Clicking **"Explain this issue"** on that finding adds a plain-language explanation and a concrete suggested fix, generated on demand.

## Current Phase

**Phase 1 (MVP) complete:** URL input, DOM scanning via Playwright + axe-core, deterministic WCAG 2.2 mapping and deduplication, on-demand LLM-based explanations, Streamlit UI, and full error handling.

**Phase 2 (planned):** repo input and a Static Code Scan Agent (ESLint jsx-a11y or AST/regex checks), extending the planner to route between URL and repo input, and reintroducing LLM-based aggregation specifically for cross-source deduplication — matching semantically equivalent findings reported differently by two separate scanners, which is a real judgment call rather than the mechanical single-source matching used in Phase 1.

## Limitations & Responsible Use

- Automated tools catch roughly a third to half of real WCAG failures — this is a floor, not a certification. A clean scorecard does not mean a page is fully accessible.
- WCAG criterion and level are extracted directly from axe-core's own rule metadata, which is more reliable than LLM-based mapping — but axe-core's tagging is not perfectly current with the latest WCAG version. For example, `duplicate-id-active` is tagged with criterion 4.1.1, which was removed/made obsolete in WCAG 2.2; the app flags this explicitly rather than presenting an outdated criterion as current.
- On-demand LLM explanations are generated per finding and should be reviewed, not applied blindly.
- This tool does not claim WCAG compliance and should not be used as the sole basis for a compliance decision.
- Only scan URLs you have permission to test.

### Streamlit UI Accessibility

This project's own Streamlit-based UI is subject to the same category of limitations it's built to detect in other sites. Streamlit's team has stated they write frontend code with accessibility in mind but has not completed a formal accessibility assessment, and Section 508 compliance is not currently supported. As a self-check, Access Agent can be pointed at its own deployed URL.
